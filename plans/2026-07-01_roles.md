# Real-prompt role schema plan

Status: design note for first proper role pass  
Date: 2026-07-01  
Scope: 19 real-prompt correct/wrong full-token traces

## Problem statement

The previous role-matched analysis was too flat and too noisy. It treated token
roles as a single label, which made it easy to compare graph states that should
not be compared directly, such as punctuation graphs versus math-number graphs.

For the next analysis pass, roles should reduce obvious target-token and span
confounds without becoming so fine-grained that prompt-level statistics lose
support. The first role pass should support grouped analysis first, with finer
labels retained for inspection and possible later drill-down.

This role plan plugs into the ADAG-lite metrics plan in
`plans/2026-07-01_new_metrics.md`.

## Grounding in observed completions

Source inspection file:

- `reports/real_prompt_19_inventory_20260701/trajectory_texts.md`

Inventory counts:

- 19 prompt pairs,
- 38 trajectories,
- 7714 generated tokens.

The completions are consistently GSM8K-style step-by-step solutions. Common
patterns:

- intro/planning: “Let's break this down”, “Here's how to solve…”;
- numbered or markdown step headers: `1. **Cost of chips:**`, `**Day 1:**`;
- prose restating givens and describing operations;
- inline arithmetic: `20 * $30 = $600`, `$2400 - $1200 - $480 = $720`;
- LaTeX-ish arithmetic: `\frac`, `\times`, braces, `$...$` delimiters;
- intermediate conclusions: “so he has 35 cars left”;
- final calculation or final summary;
- explicit answer statement: `Final answer: X`;
- `<end_of_turn>` stop token.

Approximate token-class counts from the neutral inventory showed the expected
support shape:

| Rough token class | Count |
|---|---:|
| prose/reasoning words | ~2870 |
| numeric tokens | ~1724 |
| whitespace | ~782 |
| punctuation | ~719 |
| math operators | ~491 |
| math-reasoning words | ~428 |
| currency/percent/unit symbols | ~250 |
| answer-discourse tokens | ~93 |
| stop tokens | 38 |

This argues for grouped, tiered roles. Very fine labels are useful for review,
but not as primary strata in the first statistical analysis.

## Versioning policy

Use versioning, but do not over-apply it during early role refinement.

Recommended workflow:

1. Iterate freely on regexes and manual review against the existing traces.
2. Once the first role table is good enough for analysis, freeze it as
   `roles_v1`.
3. Only create a new version when the role contract changes materially or when an
   analysis result needs reproducible comparison against an older role table.
4. If two reasonable interpretations remain, allow explicit variants, e.g.
   `roles_v1_conservative` and `roles_v1_math_expanded`, rather than creating a
   new version for every small regex tweak.

Do not bake role labels into graph profile extraction. Roles should remain a
replaceable table joined by token key.

## Decisions recorded 2026-07-01

Primary analysis goal:

- The headline question is temporal stability evolution over the chain of
  thought: does graph stability stay flat, increase, or fall as generation
  progresses?
- Analyze this evolution by region and broad token group, then compare correct
  and wrong trajectories at the prompt-pair level.
- Stable-core/substructure discovery is secondary. It should support and explain
  the temporal-stability signal, not replace it as the headline analysis.

Role granularity decisions:

- Keep `problem_setup` distinct from `work_step` for v1, even though their regex
  and review rules may share substantial logic.
- Fold final-answer marker tokens and final-answer number tokens into the broad
  `answer_core` analysis group for v1. Splitting marker versus answer quantity is
  an explicit early ablation/test after the baseline plots exist.
- Include `unit_symbol` in `math_core` for v1. Separating currency/percent/unit
  markers is also an explicit later ablation.
- Avoid making fine roles the headline statistical strata. Use fine roles for
  review/debug and later drill-down only.

Formatting decisions:

- Exclude pure horizontal whitespace from primary temporal-pair construction and
  headline plots.
- Keep newline/list/markdown formatting tokens as `formatting_control` when they
  mark structure rather than just spacing. They should appear in separate control
  plots with the same units and normalization as headline groups.
- Keep sentence punctuation outside math as `punctuation_control`, also in
  separate control plots.

Whitespace/newline rule for v1:

- `pure_horizontal_whitespace`: token text contains only spaces/tabs and no
  newline. Keep it in the role table for reconstruction, but exclude it from
  primary pair manifests and from default formatting-control plots.
- `structural_newline`: token text contains one or more `\n`. Keep as
  `format_marker` / `formatting_control`, because newlines often mark list/step
  structure in these traces.
- `indentation`: token text contains multiple spaces at the start of a line or
  immediately before a bullet/list/markdown marker. Keep as
  `formatting_control` if detectable from token offsets; otherwise treat as
  `pure_horizontal_whitespace` and exclude from headline analysis.
- `markdown_marker`: `**`, bullet markers, numbered-list markers, and colon/bold
  heading delimiters in step headers. Keep as formatting controls.

This keeps potentially meaningful formatting structure while preventing bare
space tokens from dominating adjacent-pair counts.

Review decision:

- Before freezing `roles_v1`, manually inspect a stratified sample of 5--7
  trajectories. The sample should cover both waves, correct and wrong outputs,
  near-equal-length pairs, larger length-difference pairs, and at least one weird
  wrong/caveat-style trajectory.

Initial review sample:

| `v1_prior9` | 486 | wrong | `486_wrong_seed3000_attempt000001` | short wrong answer with approximate numeric result |

Normalization decisions:

- Use two position normalizations:
  1. global generated-token fraction within each trajectory,
  2. region-relative fraction within each assigned region.
- Headline summaries should be prompt-normalized: compute trajectory/prompt-pair
  summaries first, then average across prompts so long completions do not receive
  more weight merely because they have more tokens.
- Always keep raw token counts/support counts beside normalized summaries.

## Role table contract

Each generated token should receive these fields:

```text
wave,prompt_id,label,trajectory_name,generated_index,
region,span_type,token_group,fine_role,tags,confidence,role_notes
```

Stable key:

```text
(wave, prompt_id, label, generated_index)
```

Required principles:

- `region` captures solution phase.
- `span_type` captures local span context.
- `token_group` is the primary analysis grouping for initial plots/statistics.
- `fine_role` is optional/debug-oriented and should not be the default
  aggregation tier.
- `tags` carry secondary facts such as `latex`, `currency`, `percent`,
  `inside_equation`, `answer_region`, `low_confidence`.

## Tier 1 — region

`region` should be span-level and relatively coarse.

| Region | Meaning | Examples |
|---|---|---|
| `intro_planning` | Generic opening / planning phrase before task-specific work. | “Let's break this down step by step”; “Here's how to solve…” |
| `problem_setup` | Restating givens, defining variables, identifying quantities before arithmetic steps. | “Let C be…”, “James runs 12 miles/day…” |
| `work_step` | Main step-by-step reasoning/calculation body. | numbered steps, body equations, intermediate conclusions |
| `final_calculation` | Last computation or aggregation immediately before answer statement. | `$9000 - B = 2000`; `$2400 + 600 = 3000` |
| `answer_statement` | Explicit final-answer phrase and final answer value. | `Final answer: 120`, `**Final answer: 27000**` |
| `stop` | Special generation terminator. | `<end_of_turn>` |
| `unknown_region` | Low-confidence fallback. | malformed or ambiguous spans |

Default region assignment can be rule-based:

1. `stop`: stop token.
2. `answer_statement`: from final-answer marker through stop, unless the marker
   appears earlier in a heading and is clearly not the final answer.
3. `final_calculation`: short window before answer marker that contains the final
   equation/result, preferably detected by the last arithmetic expression or final
   “therefore” conclusion.
4. `intro_planning`: prefix before the first concrete step/given/equation.
5. `problem_setup`: variable definitions and givens before main operations.
6. `work_step`: remaining solution body.

Manual/review attention should focus on boundaries between `work_step`,
`final_calculation`, and `answer_statement`.

## Tier 2 — span_type

`span_type` captures local context. It can be more detailed than `region`, but
should still have enough support for grouped analysis.

| Span type | Meaning | Examples |
|---|---|---|
| `step_header` | Step label/title, often markdown/list formatted. | `1. **Cost of chips:**`, `**Day 2:**` |
| `reasoning_prose` | Natural-language reasoning or restatement. | “She bought”, “there are”, “so he has” |
| `math_expression` | Arithmetic expression or equation span. | `20 * $30 = $600`; `\frac{3}{5}` |
| `intermediate_result` | Local result statement outside or after equation. | “= 35 cars left”, “so the total is…” |
| `final_answer_marker` | Marker phrase introducing final answer. | `Final answer:`, `**Answer:**` |
| `formatting` | Markdown/list/spacing scaffolding not part of reasoning. | `**`, bullets, list numbering, pure whitespace |
| `latex_format` | LaTeX/math formatting tokens. | `\frac`, `\times`, `{`, `}`, `$` |
| `stop` | Stop token span. | `<end_of_turn>` |
| `unknown_span` | Fallback. | ambiguous/malformed spans |

Important distinction: punctuation inside `math_expression` should not be treated
like sentence punctuation. For example, `.` in `$1200.00` or `:` in a step header
has a different role than a sentence-ending period.

## Tier 3 — token_group

`token_group` is the recommended default grouping for the initial metric plots.
It should avoid excessive fragmentation.

| Token group | Meaning | Examples |
|---|---|---|
| `reasoning_text` | Prose tokens carrying the reasoning narrative. | “calculate”, “remaining”, “therefore”, entity words |
| `math_quantity` | Numeric quantities, including integers, decimals, and fraction tokens. | `50`, `0.10`, `3/5`, `10800` |
| `math_operator` | Arithmetic/equality operators and operator words. | `+`, `-`, `*`, `/`, `=`, `times`, `divided` |
| `unit_symbol` | Currency, percent, and unit markers when tokenized separately. | `$`, `%`, `/hour` fragments if separated |
| `answer_marker` | Tokens marking the final-answer phrase. | `Final`, `answer`, `Answer` |
| `answer_quantity` | Final numeric answer token(s). | `120`, `27000`, `4.30` in final answer span |
| `equation_punctuation` | Punctuation/delimiters inside math expressions. | decimal point, commas in numbers, LaTeX braces, math `$` |
| `sentence_punctuation` | Punctuation outside math expressions. | `.`, `,`, `:` in prose |
| `format_marker` | Markdown/list/whitespace formatting. | `**`, bullet markers, pure whitespace/newlines |
| `stop_special` | Stop token. | `<end_of_turn>` |
| `unknown_token_group` | Fallback. | ambiguous tokens |

Initial analysis should usually aggregate over these groups, not over `fine_role`.

## Optional fine_role labels

`fine_role` can be assigned for later drill-down and review, but should not be
the primary statistical stratum in the first pass.

Useful fine roles:

- `intro_phrase`,
- `step_number`,
- `step_title_word`,
- `entity_word`,
- `operation_word`,
- `given_number`,
- `derived_number`,
- `final_answer_number`,
- `variable_symbol`,
- `operator_symbol`,
- `operator_word`,
- `currency_symbol`,
- `percent_symbol`,
- `sentence_period`,
- `equation_decimal_point`,
- `equation_equals`,
- `latex_command`,
- `latex_brace`,
- `markdown_bold`,
- `list_marker`,
- `whitespace`,
- `stop_special`.

For initial implementation, it is acceptable for many tokens to have a simple
fine role equal to their `token_group`. Fine roles should improve over time only
where they help interpretation.

## Initial analysis groupings

Use these broader groups for first-pass statistics and plots:

| Analysis group | Includes |
|---|---|
| `reasoning_prose` | `reasoning_text` outside pure formatting |
| `math_core` | `math_quantity`, `math_operator`, `unit_symbol`, `equation_punctuation` inside math spans |
| `answer_core` | `answer_marker`, `answer_quantity` |
| `formatting_control` | `format_marker`, whitespace, markdown/list tokens |
| `punctuation_control` | sentence punctuation outside math spans |
| `stop_control` | stop tokens, usually excluded from primary temporal analysis |

The first scientific plots should compare graph stability by:

1. `region`,
2. `analysis_group`,
3. `region × analysis_group` only where support is adequate.

Avoid making conclusions from very fine cells with small `n`.

Headline regions for v1:

- `problem_setup`,
- `work_step`,
- `final_calculation`,
- `answer_statement`.

`intro_planning`, `formatting_control`, `punctuation_control`, and `stop_control`
are controls or exclusions, not headline reasoning/math claims.

Headline token groups for v1:

- `reasoning_prose`,
- `math_core`,
- `answer_core`.

Formatting and punctuation controls should be plotted separately, with the same
metric units and normalization, to show whether headline behavior is just a
formatting artifact.

## Suggested role assignment algorithm

### Pass 1 — span segmentation

Process each generated completion as text plus token offsets.

1. Mark stop token.
2. Detect final-answer marker with high-precision patterns:
   - `Final answer:`
   - `Final Answer:`
   - `**Final answer:`
   - `**Answer:**`
3. Detect math spans:
   - `$...$` LaTeX/math spans,
   - expressions containing numbers plus operators/equality,
   - lines/clauses with repeated arithmetic operators.
4. Detect step headers:
   - markdown bold ending in colon,
   - numbered step starts like `1. **...:**`,
   - short heading-like clauses before body text.
5. Detect intro span before first step/math/given-heavy span.
6. Detect final calculation as last math/intermediate-result span before the
   final-answer marker.

The span pass should be deterministic and auditable. Each assigned span should
record:

- `span_id`,
- `span_type`,
- `region`,
- character start/end,
- token start/end,
- detector/rule names,
- confidence,
- short `span_notes` where useful.

### Pass 2 — token group assignment

Use token text plus span context.

Priority order:

1. stop token -> `stop_special`.
2. final answer numeric token inside `answer_statement` -> `answer_quantity`.
3. final answer marker tokens -> `answer_marker`.
4. pure markdown/list/whitespace -> `format_marker`.
5. tokens inside math span:
   - number/fraction -> `math_quantity`,
   - operator/equality/operator word -> `math_operator`,
   - `$`, `%`, currency/unit fragments -> `unit_symbol`,
   - punctuation/delimiters -> `equation_punctuation`,
   - words/units inside equation -> `reasoning_text` or `unit_symbol` depending
     on confidence.
6. tokens outside math span:
   - number/fraction -> `math_quantity`, with fine role `given_number` or
     `derived_number` if confidently known,
   - punctuation -> `sentence_punctuation`,
   - answer discourse words -> `answer_marker` only if in answer span, otherwise
     `reasoning_text`,
   - words -> `reasoning_text`.

Token-level assignment should run inside the detected span context. Token rules
may be shared across spans, but span context determines distinctions such as
`equation_punctuation` versus `sentence_punctuation` and `answer_quantity`
versus ordinary `math_quantity`.

### Pass 3 — confidence and review sidecars

Assign confidence categories:

- `1.0`: stop, exact answer marker, clear numeric/operator/format tokens;
- `0.8`: clear span-context tokens;
- `0.6`: ambiguous tokens where span detection is uncertain;
- `<0.6`: mark `low_confidence` for review.

Manual/agent review should target:

- final calculation boundary,
- math expression boundaries,
- tokens near `Final answer`,
- punctuation inside vs outside equations,
- weird wrong-answer caveats such as “approximately”, “misleading”, “assume”,
  “round”.

### Review workflow

Do not over-version during early refinement. Use iterative draft/review files,
then freeze the first satisfactory table as `roles_v1`.

Recommended files under the analysis root:

```text
roles/
  roles_regex.csv
  roles_regex_review_packet.md
  roles_review_iter01.csv
  roles_review_iter02.csv        # only if needed
  roles_v1.csv                   # frozen first reviewed baseline
  roles_v1_summary.json
```

`roles_regex.csv`:

- produced deterministically by the role classifier,
- one row per generated token,
- includes the role table contract columns plus diagnostic columns:
  `span_id`, `char_start`, `char_end`, `rule_ids`, `confidence`, `tags`,
  `review_priority`.

`roles_regex_review_packet.md`:

- human-readable packet for the selected 7-trajectory sample,
- shows generated text with token indices or compact token tables,
- highlights low-confidence tokens, final-answer boundaries, math spans,
  formatting/newline tokens, and weird/caveat spans.

`roles_review_iterXX.csv`:

- full row-per-token table, not just a patch, so it can be diffed and used
  directly by downstream code,
- carries the same schema as `roles_regex.csv`, plus:
  `review_status`, `reviewer_notes`, `source_role_file`, `review_iteration`,
- most rows can copy the regex assignment unchanged; reviewed rows override
  specific columns.

Iteration policy:

1. Generate `roles_regex.csv`.
2. Review the selected sample and write `roles_review_iter01.csv`.
3. Inspect disagreements and update regex/span rules if systematic.
4. Regenerate `roles_regex.csv` if rules changed.
5. Repeat only if the sample still shows systematic boundary/group errors.
6. Freeze as `roles_v1.csv` when acceptance criteria pass.

This workflow keeps the first frozen version meaningful while allowing free
pre-v1 refinement.

## Acceptance criteria for `roles_v1`

Before using role labels for ADAG-lite metrics:

1. Every token in `tokens.csv` has exactly one `region`, one `span_type`, and one
   `token_group`.
2. All 38 stop tokens are labeled `region=stop`, `token_group=stop_special`.
3. Every trajectory with a final-answer marker has an `answer_statement` region.
4. Every final numeric answer token is labeled `answer_quantity` with high
   confidence, or explicitly flagged for review.
5. At least 95% of tokens avoid `unknown_*` labels.
6. Primary analysis groups have enough prompt-level support for initial plots;
   fine-role cells with weak support are not used for headline claims.
7. The selected 7-trajectory review sample is inspected before freezing
   `roles_v1`; if it reveals systematic issues, expand the review sample before
   freezing.

## First metric pair families using roles

After `roles_v1` is frozen, build these pair families first:

1. Adjacent same-region temporal pairs.
2. Lagged same-region temporal pairs.
3. Final-window within-trajectory pairs.
4. Correct-vs-wrong relative-position pairs within each prompt.
5. Null controls matched by prompt/wave/label where applicable, token fraction,
   region, and broad analysis group.

These pair families should be generated deterministically from the role table and
the neutral inventory.
