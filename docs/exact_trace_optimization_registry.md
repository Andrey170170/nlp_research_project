# Exact-trace optimization and code-quality registry

Status: Current triage ledger
Last updated: 2026-08-23

## Purpose

This is the single intake and triage file for exact-trace performance ideas,
code-quality work, measurement improvements, rejected approaches, and future
experiments. It prevents useful findings from disappearing when they are not
selected for the immediate execution plan.

The active sequence remains authoritative in
[`plans/2026-07-29_exact_trace_performance_optimization_loop.md`](../plans/2026-07-29_exact_trace_performance_optimization_loop.md).
Detailed evidence and reasoning remain in the linked reports/specs. This file
records disposition and routing; it should not duplicate their full analysis.

When testing or review produces a new idea:

1. add one stable ID here before or when deciding whether to pursue it;
2. link the observation, code seam, report, or failed experiment that motivated
   it;
3. state the trigger and smallest discriminating next test;
4. mark it `planned` only when it is copied into the active plan; and
5. never delete rejected entries or reuse their IDs.

## Status vocabulary

| Status | Meaning |
|---|---|
| `immediate` | Current priority in the active plan |
| `running` | Submitted or executing; await classification before changing disposition |
| `planned` | Ordered in the active plan but not the current priority |
| `blocked` | Cannot advance until the named diagnostic or repair gate passes |
| `candidate` | Worth a bounded experiment when its trigger is met |
| `conditional` | Do not implement until named evidence establishes need |
| `research` | High semantic or architectural risk; isolate from routine optimization |
| `deferred` | Intentionally postponed by current evidence or sequencing |
| `superseded` | Preserved provenance for a plan or prepared artifact replaced before execution |
| `rejected` | Measured or reviewed as dominated/unsafe; retain to prevent repetition |
| `complete` | Implemented and accepted within the recorded scope |

## Downstream reuse boundary

A frozen point may be handed to another project, including Llama 8B top-k
transcoder tracing, only with an explicit scope card containing:

- model/provider and prompt/prefix/target fingerprints;
- project and sibling revisions plus immutable snapshot manifest;
- requested and resolved mechanism, with fallback/copy counters;
- fidelity classification and canonical comparison artifact;
- H200/CPU/RAM/walltime request and measured telemetry;
- cache/preheat protocol and known accounting limitations;
- exact versus bounded applicability statement; and
- the fallback to use outside the measured region.

Such a handoff freezes reproducibility for that measured point. It does not
promote the mechanism to a global launch default or claim transfer to a new
model/provider architecture without its own admission and fidelity gate.
